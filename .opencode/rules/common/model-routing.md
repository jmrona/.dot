# Automatic model routing

Apply this policy automatically to ordinary requests. Slash commands are optional shortcuts, not a requirement for choosing a model or agent. The root routine coordinator is the `build` agent: it handles intake, gathers and supplies context, coordinates work, and asks the human questions that require a decision. Route through the configured `openai/routine`, `openai/easy` or `openai/hard` agent profile; never rely on the caller's model inheritance or pass an optional model override unless the user explicitly requests it.

## Route by work type

- The coordinator runs on `routine`. Use it for intake, context collection, coordination, straightforward discovery, and other bounded work. Delegate a self-contained routine skill task to the visible `utility` subagent on `openai/routine`, including when the parent is running hard. Give it the complete brief, the relevant profile-calibration outcome, and any source or lookup evidence it needs. Do not ask it to read private profile data.
- Send substantive planning, architecture choices, and task decomposition to `stack-planner` on `openai/hard`. Task decomposition goes to it from any root. Design content also goes to it. Design content means design questions, alternatives, sections, the committee agenda, summaries, and design revisions. A root whose instructions say that it authors design content itself authors it instead. Use the visible `architect-reviewer` and `qa-expert` on `openai/hard` for their distinct committee perspectives when useful. The planner returns proposals, questions, risks, decomposition, and evidence to the parent. It does not run an orchestrator or seek approval itself. When the parent delegates, it relays planner questions and design sections to the human verbatim and obtains approval. It returns each answer to the same planner with its `sessionID`. When the parent delegates, it does not author design questions or design content.
- Send every independent implementation or specification review to a hard reviewer, including small and fast-path reviews. Use `code-reviewer` on `openai/hard` for implementation reviews and `architect-reviewer` on `openai/hard` for design or architecture reviews. Use the relevant checklist; the parent supplies the diff and verification evidence, and the read-only reviewer inspects the relevant files. A reviewer must not run shell commands, start another review workflow, or launch another reviewer.
- Send bounded, approved implementation and bounded investigation to `stack-specialist` on `openai/easy`. The implement command is not design approval: only implement tasks whose design and scope are approved.
- Use `complex-worker` on `openai/hard` for known difficult reasoning, integration, security, or explicitly escalated implementation or investigation work. Keep its task bounded and approved; difficulty is not permission to expand scope.

The six-criterion complexity triage remains intact. Workflow COMPLEX is not model difficulty: a complex feature may contain bounded implementation tasks suitable for easy workers, while substantive planning and independent reviews still use hard agents. Do not weaken or bypass triage to force a model choice.

## Delegation and context

The parent owns orchestration. Default to one level of nesting: a child must not launch children, ask the human, or invoke an orchestrating workflow. In particular, the parent runs committee, design, ticketing, implementation, and review workflows; children return their work, questions, and evidence to the parent. Use the native OpenCode V2 subagent tool with `agent`, `description`, and `prompt`; `background` is optional. `sessionID` is optional; omit it on new calls and use it only with the returned child ID to continue that same child and role. Never pass the parent session ID. Use `background: true` only for independent work and wait for completion notifications rather than polling. The prompt must carry the complete task brief and all context needed by that child, including relevant approvals, source material, profile-calibration outcome, and verification results. Do not assume a child receives the whole conversation. If essential context is absent, return `NEEDS_CONTEXT` to the parent rather than guessing or asking the human directly.

A discovery or utility task stays pinned to `openai/routine` even when a hard parent delegates it. Planning and reviewing stay pinned to `openai/hard` even when their requested scope looks small. A generic fallback is allowed only with the user's explicit authorisation and its required alias; otherwise, an unavailable required role is `BLOCKED`.

## Model aliases and limits

Use only `openai/routine`, `openai/easy` and `openai/hard` for agent and command model references. Use `routine` for coordination, intake, utility and discovery. Use `easy` for bounded implementation by `stack-specialist`. Use `hard` for planning, review and complex work. Verify alias availability through `opencode.models` or the current model API when provider/model configuration changes. Never invent a model ID. If a required alias is unavailable, stop and tell the parent; do not omit the required role or alias, rely on the parent's model inheritance, or silently fall back.

Reasoning effort comes only from the alias definition: `routine` is medium, and `easy` and `hard` are high. There are no per-agent or per-command effort overrides. Do not add model variants, per-agent or per-command effort overrides, or local temperature overrides. Existing user model overrides and already-running sessions are not forcibly changed. This policy directs routing but is not deterministic enforcement at runtime; verify actual routing separately when needed and report uncertainty rather than claiming a guarantee.
